# Contributing

Thanks for your interest in `traefik-http-knock`. This document covers the
repository layout, local development, the Yaegi constraints that apply to Traefik
local plugins, and the release process. User-facing documentation is in
[README.md](README.md).

## Project layout

```text
traefik-http-knock/
├── .github/workflows/ci.yml      # fmt, vet, test, test -race
├── .traefik.yml                  # plugin manifest (catalog + local plugins)
├── Dockerfile                    # Traefik image with the plugin baked in
├── Makefile
├── knock.go                      # Config, CreateConfig, New, ServeHTTP
├── auth.go                       # users, login form, cookies, sessions
├── crypto.go                     # PBKDF2, HMAC, token signing, constant time
├── ratelimit.go                  # per-IP login attempt reservation
├── response.go                   # CDN-safe response writer
├── ip.go                         # client IP extraction, normalization, keys
├── redis.go                      # minimal RESP client + bounded pool
├── cmd/knockhash/main.go         # password-hash generator
├── knock_test.go                 # middleware behaviour tests
├── auth_test.go                  # password, session, Basic and realm tests
├── auth_hardening_test.go        # CSRF, IP-grant and config hardening tests
├── response_test.go              # private response writer tests
├── crypto_test.go                # hash/token tests
├── ip_test.go                    # IP parsing tests
├── redis_test.go                 # RESP client/pool tests + Redis integration test
├── testserver_test.go            # in-process fake Redis used by the tests
├── yaegi_compat_test.go          # guards the Yaegi/stdlib-only constraints
├── docker-compose.yml            # local Traefik + Redis demo
├── .github/e2e/                  # tracked configs used by `make e2e`
├── .github/scripts/e2e-compose.sh # Traefik + Yaegi end-to-end smoke test
├── deploy/                       # k3s example manifests
└── deploy/plugin-configmap.yaml  # generated by `make k8s-plugin-configmap`
```

The test files are split by concern so each area stays reviewable; the fake
Redis server lives in `testserver_test.go` so unit tests do not need Docker.

`deploy/plugin-configmap.yaml` is generated rather than committed: the plugin
source should not be duplicated in the repository. A ConfigMap is capped at
1 MiB and is a convenience path — the custom image is the recommended production
option.

## Development

Requirements: Go 1.22+. Docker is only needed for the integration test and the
end-to-end compose demo.

```bash
make check          # gofmt check + vet + test + test -race
make e2e            # Traefik + Yaegi + Redis end-to-end smoke test
make fmt
make vet
make test
make race
```

The unit tests use an in-process fake Redis server, so no Docker is required.
They cover path mode, password login, multiple users, sessions,
logout/revocation, Basic auth, Bearer tokens, realm isolation, login rate
limiting and KDF concurrency, CSRF/origin checks, password-change IP-grant
revocation, CDN headers, PBKDF2/HMAC, and the RESP client.

Generate a password hash for tests or deployment:

```bash
make hash-password
# or: go run ./cmd/knockhash
# for a credentials-file line:
go run ./cmd/knockhash -username alice
```

### Redis integration test

```bash
make redis-up
make test-integration
make redis-down
```

Or manually:

```bash
docker run --rm -d -p 6379:6379 --name knock-redis redis:7.4-alpine \
  redis-server --requirepass devpassword
REDIS_ADDR=127.0.0.1:6379 REDIS_PASSWORD=devpassword \
  go test -run Integration -v ./...
```

### End-to-end demo

`make e2e` runs the automated version of this demo (path, password, Basic,
logout and Redis-outage checks) and is also part of CI.

```bash
make compose-up
curl -i http://localhost:8000/          # 403
curl -i http://localhost:8000/__knock__/0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
                                        # 204
curl -i http://localhost:8000/          # 200
make compose-down
```

The compose secret is a development placeholder — never reuse it. For a password
demo, point the Middleware at `authMode: password`, add a `users` entry, and
mount/set a `cookieSecret`.

## Yaegi constraints

Local plugins run inside the Yaegi interpreter
(`github.com/traefik/yaegi` v0.16.1 in Traefik v3.2 and v3.7), not the Go
runtime. Three rules follow:

1. **Standard library only.** Every import must be resolvable inside the Traefik
   image. `yaegi_compat_test.go` fails the build on any import whose first path
   segment contains a dot.
2. **No `errors.Is` / `errors.As` / `errors.Unwrap`.** Yaegi v0.16.1 panics on
   them (`*target must be interface or implement error`), and Traefik turns the
   panic into an HTTP `500`. The plugin classifies errors with direct type
   assertions on unwrapped errors instead; `yaegi_compat_test.go` enforces this.
3. **One expression per `case` clause.** Yaegi v0.16.1 evaluates only the first
   expression of a comma-separated case list instead of OR-ing the entries, so
   the rest is dead code. Unlike rules 1 and 2 this produces no panic and no
   error: `case c >= 'a' && c <= 'z', c >= 'A' && c <= 'Z':` silently accepted
   lowercase letters only, which made `clientIPHeader` reject every real header
   name and left `403` on all protected routes.
   `TestYaegiCompatAvoidsMultiExpressionCases` enforces it.

Because rules 2 and 3 only misbehave under the interpreter, `go test` cannot
catch them on its own — the static guards above are what keep the plugin inside
the Yaegi subset.

Verified live against **Traefik v3.2.5 + Redis 7.4** during development:

| Scenario | Result |
| --- | --- |
| Protected request before any knock | `403` |
| `POST` to the knock path | `403`, no Redis write, no backend call |
| `GET` to the knock path | `204`, `Cache-Control: no-store`, `Pragma: no-cache`, `X-Knock-Ttl`, Redis key `1` with `TTL 7200` |
| `GET` to the knock path with `redirectURL: /` | `303`, `Location: /`, grant stored |
| Protected request after the knock | `200`, backend reached |
| Redis stopped | `503` for knock and protected requests, no panic |
| Redis `-NOPERM` on `SET` | `503`, connection reused, no panic |

Password login, Redis session cookies, logout/revocation, the JSON Bearer flow,
PBKDF2 verification and Basic auth were also exercised under Yaegi v0.16.1 and
end to end against Traefik v3.2.5 + Redis 7.4.

## Module path and releases

The module path is **`github.com/ttgml/traefik-http-knock`** and must stay
consistent in `go.mod`, `.traefik.yml`, `Dockerfile`, `Makefile`,
`.github/workflows/ci.yml`, `docker-compose.yml`, `deploy/helmchartconfig.yaml`,
`deploy/traefik-static-config.yml`, `deploy/traefik-compose.yml` and
`cmd/knockhash/main.go`.

Traefik requires the module path to match the repository path, the local plugin
directory (`/plugins-local/src/<module>`) and the catalog `import`. If you fork
or rename the repository, change all of them together:

```bash
grep -rl 'github.com/ttgml/traefik-http-knock' . \
  --exclude-dir=.git | xargs sed -i 's|github.com/ttgml/traefik-http-knock|github.com/<you>/traefik-http-knock|g'
```

Image tags use `ghcr.io/ttgml/traefik-http-knock` in the `Makefile`, the
`Dockerfile` comment and `deploy/helmchartconfig.yaml`; adjust those too if you
push somewhere else.

### Catalog release

A catalog release requires:

* the repository path to equal the module path in `go.mod`,
* `.traefik.yml` at the repository root with `import:` equal to that module
  path,
* a semver tag such as `v0.3.0` that Traefik can resolve through the Go module
  proxy,
* no `replace` directives and no dependencies outside the standard library (this
  plugin has none).

Then release:

```bash
make release PLUGIN_VERSION=<next-version>   # runs the checks and creates an annotated tag
git push origin <next-version>
```

CI runs `fmt`, `vet`, `test`, `test -race`, the Redis integration test and the
Traefik + Yaegi end-to-end smoke test on every push and pull request; publishing
runs only for `v*` tags.

## Reporting security issues

Please do not open a public issue for a vulnerability. Contact the maintainer
privately so a fix can be prepared before disclosure.
